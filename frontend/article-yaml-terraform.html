YAML Over HCL: Making Terraform Safe for Non-Experts

Migrating 40+ inherited AWS accounts onto Terraform, the obvious approach was one codebase per environment. That approach encodes the exact drift you migrated to escape.

Reva Wiki · 2024 · 7 min read

The setup

Global compliance required GitOps-based provisioning through Terraform. What we had was years of console-era decisions across 40+ AWS accounts: inconsistent naming, stateful configurations nobody wanted to touch, and environment-specific variations that existed because somebody needed them once on a Friday.

Both facts had to become true at the same time, and delivery was not allowed to stop while it happened.

The per-environment trap

The instinctive move is a directory per environment. dev/, staging/, prod/, each with its own HCL. It feels organised. It is a trap, for two reasons.

It preserves the drift. You migrated because environments had diverged. Giving each its own codebase guarantees they keep diverging — only now the divergence is in version control and looks deliberate.

It concentrates knowledge. Three HCL codebases means the number of people who can safely change any of them is however many know Terraform well. On most teams that is two, and one of them is on leave.

A migration that hits the compliance deadline and leaves you with three diverging codebases has not solved the problem. It has renamed it.

One codebase, config-driven

What we built instead: a single Terraform module set describing every resource shape the portfolio needs, with per-environment YAML supplying the differences.

Resources filter by environment flag through for_each loops, driven by TF_VAR_env injection at pipeline runtime. The same plan command produces the right subset per environment, because the environment is an input rather than a directory.

The HCL gets written once and reviewed once. Everything that varies lives in configuration.

Configuration is an interface

This is the part that gets undersold. Choosing YAML as the edit surface is not a syntax preference — it is a decision about who is allowed to contribute.

HCL is a language. It has module semantics, state implications, and failure modes that are genuinely non-obvious. Asking an application engineer to make a safe change in HCL means asking them to learn Terraform properly first.

A YAML value is a value. The diff is readable by anyone on the review. The blast radius of a mistake is bounded by what the module permits — and the module was written by somebody who knew what they were doing, once.

The operational outcome: an engineer who does not know HCL could still safely change infrastructure. That is an organisational result achieved through a technical decision.

Standardization surfaces waste

An unplanned benefit: once every account was described the same way, the redundant and simply-forgotten resources became a list rather than a rumour.

Rightsizing, reservation optimization, and eliminating resources nobody could name cut AWS infrastructure cost for the SEA region by roughly 55%. None of that was findable while the estate was still described inconsistently.

Standardize first, optimize second. In that order, the second step is mostly reading a list.

Where this does not fit

Honest caveats, because config-driven IaC is not free:

  • The modules have to be genuinely good. All the complexity moved somewhere — into module design. A sloppy module behind a clean YAML interface is a worse outcome, not a better one.
  • Expressiveness is capped by design. If a team legitimately needs environment-specific resource shapes rather than values, you will fight the abstraction. Decide that up front.
  • Debugging gains a layer. “Why was this resource not created” now spans the YAML, the for_each, and the module. Good error messages stop being optional.

For a portfolio of similarly-shaped applications across dev, staging and production, the trade lands firmly on the config-driven side.
