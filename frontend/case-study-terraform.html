Console → Terraform at 40+ AWS Accounts

Global compliance required GitOps-based provisioning. The estate we inherited was click-ops across 40+ accounts, with naming drift and environment-specific snowflakes everywhere. Both things had to be true at once, without stopping delivery.

Context

PT HM Sampoerna is part of Philip Morris International, which means its cloud estate answers to PMI's global security and governance standards — not just local ones. I joined as Senior DevOps Engineer owning SLAs for the application portfolio, and led a team of 7 engineers through the migration.

The mandate: move highly critical application infrastructure off console-based provisioning and onto Terraform, with a consistent GitOps branching strategy across dev, staging, and production.

The problem

Inherited estates are rarely clean. This one had accumulated years of console-era decisions across 40+ accounts: inconsistent naming, stateful configurations nobody wanted to touch, and environment-specific variations that existed because someone once needed them on a Friday.

The obvious approach — write Terraform per environment — reproduces the drift in code instead of removing it. You end up with three codebases that diverge quietly, and a team where only two people can safely change any of them.

Compliance wanted GitOps. Operations wanted to not be blocked. A three-codebase HCL sprawl would have satisfied the first and destroyed the second.

The YAML approach

Instead of per-environment Terraform, I built a single config-driven codebase: one set of HCL, with per-environment YAML supplying the differences.

  1. One codebase

    A single Terraform module set describing every resource shape the portfolio needs — written once, reviewed once.

  2. Per-environment YAML

    Environment differences live in configuration files, not in forked HCL. Dev, staging and production read the same modules with different inputs.

  3. for_each + TF_VAR_env

    Resources filter by environment flag through for_each loops, driven by TF_VAR_env injection at pipeline runtime — so the same plan command produces the right subset per environment.

  4. GitOps branching

    Dev, staging and production map to branches with the review gates compliance required, making promotion a reviewable diff rather than a console action.

The result that mattered most operationally: an engineer who doesn't know HCL can still safely change infrastructure, because the thing they edit is a YAML value with a reviewable diff.

Cost work

Standardization surfaces waste. Once every account was described the same way, the redundant and simply-forgotten resources became visible as a list rather than a rumour.

Rightsizing, reservation optimization, and elimination of redundant and unused resources cut AWS infrastructure cost for the SEA region by ~55%.

Jenkins automation

Separately from the migration, the team was absorbing 1–2 hours per day of repetitive service-request work — the kind of task that's individually trivial and collectively a whole headcount.

Targeted Jenkins automations removed that entirely, freeing team capacity for the migration itself rather than the ticket queue around it.

Outcome

Compliance achieved without blocking operations. 40+ legacy accounts aligned to PMI global standards, SEA cloud spend down ~55%, and 1–2 hours of daily toil removed from the team's day.

The durable win is the one that doesn't appear in a metric: the team no longer needed a Terraform specialist in the room to make a safe change.

Lessons

  • Don't encode drift. Writing per-environment Terraform preserves exactly the inconsistency you migrated to escape.
  • Configuration is an interface. Choosing YAML over HCL as the edit surface decided who on the team could contribute — that's an org outcome, not a syntax preference.
  • Standardize first, then optimize. The ~55% cost reduction was only findable after everything was described consistently.
  • Compliance deadlines are not an excuse to ship sprawl. The constraint made the design better, not worse.
